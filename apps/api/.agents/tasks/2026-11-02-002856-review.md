# LHD backend API: NestJS modular monolith (content, auth, users/progress, curriculum-grounded AI)

Four commits build out `apps/api` on top of the content foundation: a NestJS 11 modular monolith scaffold with a mirrored `@lhd/shared` contract and a repository abstraction (FEAT-001), a read-only content module serving curriculum phases (FEAT-002), JWT auth with a Roles guard plus caregiver-scoped users/progress and DPDP data-rights (FEAT-003), and a RAG-style AI assistant grounded only in the curriculum with a health/safety guardrail plus an e2e smoke test (FEAT-004). The design keeps child-data protection structural: a single `CaregiverAccessService` is the only place the self/admin/linked-caregiver rule lives, and every user-scoped read/write routes through it. Build and test run with in-memory repositories and a deterministic AI stub, so no live database or network is required.

Watch for: nothing blocking. All four commands pass independently and every required behaviour is verified in source. (confirmed)

**Verdict**: APPROVED

## High-level view

The persistence layer picks in-memory repositories unless `DATABASE_URL` is set; the choice is made once at module construction, so build, unit tests, and e2e never touch a database or network. The Prisma implementations are wired but inert by default, and `prisma generate` is deliberately kept out of build/test.

Access control is centralised. `CaregiverAccessService.canAccess` grants access to self, admins, and caregivers with an existing link, and both `ProgressService` and `UsersService` call only this method — there are no scattered ownership checks to drift out of sync. The `RolesGuard` is orthogonal: it passes through when no `@Roles` are declared and throws `ForbiddenException` when the authenticated role is not in the list.

The AI assistant runs the safety guardrail before anything else. Health, safety, and wellbeing questions return a fixed, non-authoritative message pointing to a caregiver, teacher, doctor, or emergency help, with no curriculum answer and no citations. Non-health questions are answered only from passages retrieved out of the loaded curriculum and composed by a deterministic offline stub, so answers are grounded by construction.

The mirrored contract in `apps/api/src/shared/contract.ts` is byte-identical to `packages/shared/src/index.ts` below the header, so the shared contract has not diverged. The change set touches only `apps/api` plus additive root `test:api`/`dev:api` scripts and the lockfile; no `packages/*`, `tools/`, or other app was modified.

### Persistence selection keeps build and test offline

`PersistenceModule` computes `useDatabase = hasDatabaseUrl()` once at module construction and provides either the three in-memory repositories or the three Prisma-backed ones. With `DATABASE_URL` unset — the default in tests and e2e — the in-memory Maps are used, so no database connection is attempted. The Prisma service loads `@prisma/client` through a guarded dynamic require, so tsc and Jest need no generated client, and `prisma generate` is kept out of the build and test scripts. The e2e test confirms this end to end: it boots the full `AppModule` with in-memory repos and the AI stub, with no DB or keys.

### CaregiverAccessService as the single access-control choke point

`CaregiverAccessService.canAccess(actorId, actorRole, subjectUserId)` returns true for self (`actorId === subjectUserId`), for `admin`, or when a `CaregiverLink` exists via the repository. `ProgressService` calls it in a private `assertAccess` before both reads and writes, throwing `ForbiddenException` on denial; `UsersService` and the data-rights endpoints authorise through the same service. Centralising the rule is what makes the DPDP "role-based access on every read/write" guarantee structural rather than per-handler.

```
request ──JWT──> JwtAuthGuard ──> controller
                                     │ actor = request.user {userId, role}
                                     ▼
                         ProgressService / UsersService
                                     │
                                     ▼
                         CaregiverAccessService.canAccess
                          (self | admin | linked caregiver)
                                     │
                                     ▼
                              repository (in-memory | Prisma)
```

The `RolesGuard` is a separate concern: it reads `@Roles(...)` via the reflector over handler and class, passes through when none are declared, and throws `ForbiddenException` when the authenticated role is not in the list. Caregiver-only routes (`POST /api/users/links`, `/minors`) are decorated with `@Roles('parent','guardian','educator','admin')`.

### AI guardrail routes health/safety questions before any retrieval

`AiService.ask` calls `classifyAndGuard` first. The guardrail matches a broad health/safety/wellbeing keyword set case-insensitively on word boundaries, so "ill" does not fire on "skill" and "fall" does not fire on "fallacy". On a match it returns `routedToHuman: true` with the fixed `HUMAN_HELP_RESPONSE` — which points to a parent/guardian, teacher, or doctor plus emergency services and explicitly states it cannot give medical, diagnostic, or treatment advice — and no curriculum answer and empty citations. This directly enforces the non-negotiable "strengthen, never replace" product rule.

### Retrieval grounded only in curriculum content

Only when the guardrail does not fire does `AiService` call `Retriever.retrieve`, which scores passages built lazily from every loaded phase (via `ContentService`) by keyword overlap and returns the top-k with citations. The default `StubLlmProvider` composes an extractive answer purely from those passages — no network, no randomness — and returns a safe "could not find anything in the curriculum" message when retrieval is empty. Because the answer is assembled only from retrieved passages and tagged with phase citations, grounding holds by construction. The provider sits behind the `LLM_PROVIDER` token so a real model can be swapped in without touching the grounding logic.

### Content serving and 404 behaviour

`ContentController` exposes `GET /api/phases` (catalog entries) and `GET /api/phases/:idOrSlug`, matching by id or slug and throwing `NotFoundException` (404) when unknown. The loader reads `catalog.json` at runtime and loads only phase files present on disk, skipping malformed or id-mismatched phases with a warning rather than throwing, so the app still boots on partial content. The e2e smoke test boots Nest and asserts `GET /api/phases` is 200 with an entry whose id is `phase-01`.

### Mirrored contract has not diverged

`apps/api/src/shared/contract.ts` carries the source-of-truth header and is byte-identical to `packages/shared/src/index.ts` below the first export, confirmed by a whole-body comparison. The same 15 type/interface/enum names are exported from both. Imports across the app use the relative mirror rather than `@lhd/shared`, which keeps the CommonJS build buildable while preserving the contract.

### Change scope and DPDP posture

The diff touches only `apps/api` plus additive root `test:api` and `dev:api` scripts and the lockfile; the existing root `test`/`content:validate` scripts are unchanged and no `packages/*`, `tools/`, or other app was modified. DPDP protections are present: minor accounts are caregiver-mediated (`createMinorAccount` requires a caregiver role and auto-links), `PublicProfile` never exposes `passwordHash`, role-based access runs on every user-scoped read/write through the choke point, and `GET /api/users/:id/export` plus `DELETE /api/users/:id` give exportable/deletable data — all authorised through `CaregiverAccessService`.

### Independent verification

From `apps/api`: `npm run build` exits 0 with no TS errors; `npm test` is green (12 suites, 53 tests); `npm run test:e2e` is green (1 suite, boots Nest, `GET /api/phases` 200 with `phase-01`). From repo root `npm run content:validate` is green (13/13 phases). Not independently re-run: the Prisma/Postgres code paths (inert by default, not exercised without a live DB) and the real LLM provider path (no provider bound by default). These are out of scope for the no-DB/no-network requirement.

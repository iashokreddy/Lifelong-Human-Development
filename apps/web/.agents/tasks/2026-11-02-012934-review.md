# @lhd/web — Next.js App Router web app over the curriculum API

A new Next.js 15 App Router + TypeScript app at `apps/web` renders the 13-phase lifelong-development curriculum served by the existing NestJS API, plus a grounded learning assistant. Data flows through a single non-throwing `lib/api.ts` client (discriminated `Result`, `cache: 'no-store'`), so server components render empty states instead of crashing when the API is down — this is what lets `next build` complete offline. Types come exclusively from `@lhd/shared` (transpiled via `transpilePackages`), and the "strengthens and never replaces" philosophy is woven through the layout, a principle banner, and the assistant. Scope is clean: only `apps/web` plus two additive root scripts (`dev:web`, `test:web`) changed; `packages/content`, `packages/shared`, `tools/`, `apps/api`, `apps/mobile` are untouched and the root `test` script still runs `content:validate`.

Watch for: the test runner was switched from the mandated Vitest to Jest because the workspace path ends in `%`, which breaks Vite's `decodeURI` — documented and justified (confirmed). No functional gaps found against the requirements.

**Verdict**: APPROVED

## High-level view

The data layer is a single `request<T>` wrapper that converts every network or non-2xx outcome into `{ ok: false, error }`. Every page awaits a `Result` and branches to an `EmptyState` on failure, which is the structural reason the offline build cannot crash. Independently re-ran: `next build` compiles with 0 errors and 6 routes while the API is down.

The route surface matches the contract exactly: `/` (ordered 13-node timeline + principle banner), `/phases` (ordered card grid), `/phases/[idOrSlug]` (full `PhaseView` with prev/next derived from catalog order), and a client-only `/assistant` form that posts to `/ai/ask` and renders the answer, human-routing treatment, and citation links. `PhaseView` renders every `Phase` field in the shared type — domains (via readable-label map), year plans, daily/weekly activities, parent guidance, milestones, safety, outcomes, projects, app features, and source links — with field access matching `@lhd/shared` one-for-one.

Accessibility is built in structurally: one `h1` per page (asserted by test), semantic landmarks, a skip link, a labelled assistant textarea, a visible `:focus-visible` outline, and an accessible stretched-link card pattern. The theme uses dark text on light surfaces with a dedicated high-contrast focus colour.

The philosophy rule is present in UI copy in three places (header/footer layout, `PrincipleBanner`, assistant reassurance note), and the assistant surfaces `routedToHuman` so health/safety questions visibly defer to a human.

The only deviation is the Jest-for-Vitest swap, forced by the `%` in the absolute path and documented in both `VERIFICATION.md` and `FEAT-001` findings. It does not weaken coverage: 21 tests across the API client, domain labels, and full `PhaseView` rendering all pass.

### Non-throwing API client as the offline-build guarantee

`lib/api.ts` centralises all fetching in one `request<T>` helper that wraps `fetch(url, { cache: 'no-store', ...init })` and returns a discriminated `Result<T>`: a non-2xx response becomes `{ ok: false, error: '...status N' }` and a thrown/rejected fetch is caught and becomes `{ ok: false, error }`. Nothing propagates. Because the home, phases, and phase-detail server components all `await` a `Result` and render an `EmptyState` on `ok: false`, `next build`'s data-collection and static-generation phases cannot throw when the API is unreachable. I re-ran `npm run build` with no API running: 0 errors, 6 routes emitted (`/`, `/_not-found`, `/assistant`, `/phases`, `/phases/[idOrSlug]`), matching `VERIFICATION.md` (confirmed). The base URL reads `process.env.NEXT_PUBLIC_API_BASE_URL` and defaults to `http://localhost:3001/api` (confirmed).

### Route surface and full Phase rendering

`PhaseView` reads every field defined on `Phase` in `@lhd/shared` and each access lines up with the type: `ageRange.label`, `title`, `primaryObjective`, `summary`, optional `guidingPrinciple`, `developmentDomains[].{domain,focus}`, `yearPlans[].{label,objectives,capabilities}`, optional `activities.{daily,weekly}`, optional `parentGuidance`, `milestones`, `safety`, `outcomes`, `projects`, `appFeatures`, and `sources` (rendered as external links with `rel="noopener noreferrer"`). Optional arrays are guarded with `?? []` and length checks, so phases that omit daily/weekly activities or parent guidance render cleanly. Prev/next are computed by sorting the catalog on `order` and locating the current phase by `id`, degrading to no pager when the catalog fetch fails — consistent with the non-throwing posture (confirmed).

The milestones section leads with "Age ranges are indicative guides, not rigid limits," honouring the steering rule that age ranges are indicative (confirmed).

### Assistant: grounding, citations, and human routing

`/assistant` is the only client component. It posts the trimmed question to `askAssistant`, renders the plain answer or, when `routedToHuman` is true, a bold "This is a question for a trusted human" lead-in before the API's human-help text. Citations render as links to `/phases/${citation.phaseId}`; since the API emits phase ids like `phase-01` and the detail route accepts id or slug, these resolve (confirmed against `ai.service.ts`, which carries `phaseId` through from retrieved passages). A persistent `role="note"` reassurance block states the assistant strengthens and never replaces a parent, teacher, or doctor, and that health/safety/wellbeing questions route to a human. On API failure the catch-branch message itself reminds the user a trusted adult can help — the philosophy holds even in the error path (confirmed).

### Accessibility posture

One `h1` per page: the home hero, `/phases`, the assistant, and `PhaseView` each own the single `h1`, and the `PhaseView` test asserts exactly one `h1` containing the title. Section headings use `aria-labelledby` against stable ids. The layout provides a skip link to `#main-content`, a `<main>` landmark, and labelled `<nav>` landmarks. The assistant textarea has an explicit `<label htmlFor>`. `globals.css` defines a `:focus-visible` outline in a distinct focus colour (`--focus: #b4532a`) and the theme pairs dark text (`#1f2522`) on light surfaces. The `PhaseCard` stretched-link uses `position: relative` on the card with a `::after` overlay on a real anchor, keeping the link keyboard-focusable with accessible text rather than making a non-semantic div clickable (confirmed).

### Scope and protected boundaries

`git diff` against the API baseline shows changes confined to `apps/web`, `package.json`, and `package-lock.json`. The root `package.json` diff adds only `dev:web` and `test:web`; `test` still equals `npm run content:validate`. A targeted diff over `packages/content`, `packages/shared`, `tools`, `apps/api`, and `apps/mobile` returns empty (confirmed).

### Test coverage and the runner deviation

Three suites, 21 tests, all passing on an independent run. `api.test.ts` verifies URL construction for `getPhases`/`getPhase`/`askAssistant`, the `no-store` cache flag, the bearer header presence/absence, the `{ question }` body, and that both network rejection and non-2xx resolve to `{ ok: false }` without throwing — directly exercising the offline-safety contract. `domain-labels.test.ts` covers all 15 enum keys plus the title-case fallback. `PhaseView.test.tsx` renders every major section and asserts readable domain labels (`Physical & motor`, not `physical-and-motor`) and the single-`h1` rule.

Not tested: the page-level server components (`page.tsx` files) and the assistant's interactive submit/loading/error state transitions have no direct unit tests — those paths are covered only indirectly by the recorded runtime HTML probe. Low risk given their thinness, but worth noting.

The runner is Jest via `next/jest`, not the mandated Vitest, because Vite 5 calls `decodeURI` on the project root and the trailing `%` in `…Evaluation of Human 0 to 100%\` throws `URIError: URI malformed`. The rationale is recorded in `VERIFICATION.md` and `FEAT-001`. This is a justified environmental deviation, not a shortcut (confirmed).

### Verification evidence

`VERIFICATION.md` records all four required checks as PASS: offline build, lint, tests, and a runtime HTML probe that started the real API (after the `Loaded 13 phase(s) of 13 catalog entries` log) and web server, asserted real content (`Foundations`, `strengthens and never replaces`, `Serve and return`, `Physical &amp; motor`) on `/` and `/phases/phase-01`, then stopped both servers and deleted the temp probe. I independently reproduced checks 1–3 (build 0 errors API-down, lint clean, 21 tests passing); the runtime probe is accepted from the recorded evidence (confirmed for 1–3, evidence-based for 4).
